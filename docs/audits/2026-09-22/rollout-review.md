# Ops Toolshed: company rollout review

> Historical baseline: this review records findings at the source snapshot below. Remediation is in progress in the working tree. Use [rollout validation](../../rollout-validation.md) and current test results before treating any finding as closed.

**Review date:** 22 September 2026  
**Source:** `r1.9` at `8e3df928e8c9ba00f2b472bdf231609e2ca8c8e7`, including the working-tree changes present during this review. The tree was already modified; this audit preserved those changes.  
**Decision:** **Do not roll out company-wide yet.** A contained pilot with informed Prisma users is reasonable after the two clipboard findings, the broken Approvers paste workflow, and the approval-polling race are repaired and validated in Chrome. A company-wide release needs the remaining gates below.

This is a source, test, and offline-probe assessment. I did not install or reload the extension, access signed-in Prisma, Meta, or SharePoint, inspect the distributed ZIP, or run a browser performance profile. Vendor and enterprise policy behaviour therefore remains unverified. The tests establish the implemented contracts represented in Jest; they do not establish live Prisma correctness.

The Codex Security workbench sealed scan `d2d3931b-6648-4064-bc17-873d2aa7c53a` with two **Medium** findings and **partial** source coverage. It warned that the working tree changed during the scan because the audit artifacts and mandatory build metadata were written; the implicated clipboard source files were not edited. The generated workbench report is under the scan's temporary protected directory, while this file is the accessible, reviewable handoff.

## Findings and required action

| Priority | Finding and evidence | Impact | Required outcome |
| --- | --- | --- | --- |
| **Blocker** | **Favourites can reach an OS clipboard paste from a synthetic page click.** The Favourites handler lacks the `event.isTrusted` guard used by Paste Approvers ([`features/approver-pasting.js:1133-1174`](../../../features/approver-pasting.js)). The paste loop sends `copyToClipboard`, does not check its result, then invokes `document.execCommand('paste')` ([`features/approver-pasting.js:1187-1203`](../../../features/approver-pasting.js)). The background router does not expose that action ([`background/message-handlers.js:466-498`](../../../background/message-handlers.js), [`background.js:269-275`](../../../background.js)). Under native clipboard conditions, a synthetic click could paste pre-existing sensitive clipboard content into page-readable DOM. Browser-native transfer was **not** exercised; source reachability and the unsupported action were confirmed. | Potential clipboard disclosure; real Favourites clicks can paste stale content. | Require a genuine user event, stop on any failed write, and preferably insert the known email through the native Select2 control without using the OS clipboard. Test synthetic clicks, failed writes, and a harmless clipboard sentinel in signed-in Chrome. |
| **Blocker** | **A page script can trigger a privileged clipboard write.** The campaign-name delegated `pointerdown` handler reads page-mutable `data-full-text` and sends it for copying without a trusted-event check ([`features/campaign.js:1049-1064`](../../../features/campaign.js)). The worker validates sender and nonblank text, then forwards it to the offscreen clipboard writer ([`background/message-handlers.js:195-205`](../../../background/message-handlers.js), [`background.js:193-205`](../../../background.js), [`offscreen.js:45-57`](../../../offscreen.js)). | A compromised Mediaocean page script can replace the user's system clipboard with arbitrary text without an intentional copy action. This is a clipboard integrity issue; clipboard reading is not established by this path. | Reject synthetic events at every page-event entry to privileged copy. Cover campaign name/header, Order ID, and URL copy with regression tests and a controlled browser check. Preserve the existing worker sender checks. |
| **Blocker** | **Paste Approvers and Favourites currently use an unsupported clipboard action.** [`features/approver-pasting.js:1187-1198`](../../../features/approver-pasting.js) sends `copyToClipboard`; the message-handler table has no such entry and returns `Unknown action`. Existing feature tests mock this message as success, so they miss the integration failure. The offline probe in [`validate-findings.cjs`](validate-findings.cjs) confirms the route mismatch. | The selected address is never copied before the native paste; an old clipboard value may be pasted. Approver selection is a high consequence workflow. | Fix the complete content-script → worker → input path and add an integration contract against the real router. Verify a multi-address paste and clipboard restoration in both current and legacy Approver UIs. |
| **Blocker** | **Approval polling can lose a newly submitted campaign.** [`background/approval-polling.js:130-211`](../../../background/approval-polling.js) reads the whole pending map, awaits one or more network requests, then writes the old map. A concurrent `trackCampaignApproval` writes the new campaign to storage; the poll's later write removes it. The offline probe reproduces this interleaving with mock storage and fetch. | A campaign may silently stop being tracked immediately after submission, so the promised approval notice never arrives. | Serialize all pending-map changes or merge poll results against a fresh storage read under one shared write queue. Test concurrent add, dismiss, disable, and delayed/failed fetch paths. |
| **Rollout gate** | **Non-Prisma onboarding has no dedicated path.** Installation opens [`onboarding.html`](../../../background.js) for everyone, and the setup and final action are Prisma-specific ([`onboarding.js:22-25`](../../../onboarding.js), [`onboarding.js:150-167`](../../../onboarding.js)). Skip sends the user to Settings; it does not record an explicit role. The master Features-off switch disables extension pages as well as Prisma enhancements ([`extension-page-gate.js`](../../../extension-page-gate.js)). | Company-wide recipients who do not book on Prisma are led toward irrelevant setup, while switching off features removes potentially useful shared tools. | First screen: **“I use Prisma”** and **“I don't book on Prisma.”** Save a reversible role choice. The latter should receive a short tour of relevant popup, timesheet, Help Guides, Approvers, or Social Booking tools as applicable, with no Prisma navigation, Prisma login prompt, campaign tour, history, or approval polling. Keep shared tools accessible; do not use `allFeaturesDisabled` as a role flag. Allow change of role in Settings. |
| **Rollout gate** | **Sensitive data disclosures are materially inaccurate.** README says all preferences are exclusively local and that communication is limited to Mediaocean, SharePoint, and optional Meta API ([`README.md:61`](../../../README.md), [`README.md:130-131`](../../../README.md)). Preferences and Help Guide favourites use `chrome.storage.sync` ([`background/feature-mode.js:22`](../../../background/feature-mode.js), [`help-guides.js:625`](../../../help-guides.js)); extension pages fetch Google Fonts and cdnjs CSS ([`approvers.html:8-13`](../../../approvers.html), [`settings.html:8-9`](../../../settings.html)). Campaign history stores client/campaign references locally ([`features/campaign-history.js:487-575`](../../../features/campaign-history.js)); Meta tokens are stored locally ([`social-finance.js:8`](../../../social-finance.js)). | An internal auditor cannot approve retention, sync, recipients, and permission requests from the current statement. The remote stylesheet request does not by itself prove campaign data is sent to those providers. | Publish a plain-English data-flow table: feature, data, source, storage area, optional Chrome Sync behaviour, destination, retention/deletion, and owner. Correct README and onboarding; explain optional Meta token handling and diagnostics export. Have privacy/security owners sign off. Prefer bundling fonts/icons and removing remote CSS dependencies if practical. |
| **Rollout gate** | **The release mechanism is manual unpacked installation.** README tells staff to download a ZIP, extract into Documents, replace files, and reload Chrome ([`README.md:16-53`](../../../README.md)). CI runs Jest but does not package, hash, sign, or publish an immutable artifact ([`.github/workflows/tests.yml`](../../../.github/workflows/tests.yml)). `outputs/` contains tracked business-workbook and preview artifacts and is not in `.gitignore`. | Broad deployment lacks reproducible payload provenance, controlled updates/rollback, and a clearly defined release file list; accidental inclusion of nonproduct data is possible. | Create a reproducible release ZIP from an allowlist, publish its hash and commit, verify no `outputs/`, tests, samples, or credentials ship, and document owner, version, update and rollback. For large-scale installation, have IT assess managed Chrome distribution or domain publication rather than relying on individual Developer mode installs. Review tracked `outputs/` with its data owner before removal or history action. |
| **Rollout gate** | **`Max Campaign Budget` edits a financial field via a live native editor.** [`features/max-campaign-budget.js:483-535`](../../../features/max-campaign-budget.js) reuses any visible editor before proving it belongs to the selected cell. An editor left on another cell can therefore receive a value. The outer error handler reports an error but does not always restore a prior probe or correction ([`features/max-campaign-budget.js:862-867`](../../../features/max-campaign-budget.js)). This is a source-backed risk; incorrect-cell or failed-restore behaviour needs live reproduction. | A wrong or partial unsaved booking value may remain for the user to save. | Bind each write to verified grid coordinates/selected cell, prevent changing selection during the operation, check old/new cell values after each commit, and restore on every failure path. Test single and multi-row Buy and Actualise cases with a pre-opened editor, route change, timeout, and rounding. Obtain booking-owner sign-off before enabling by default at scale. |
| **Improve before wide scale** | **Performance coverage is narrower than the workload.** The central observer benchmark measures scheduling only and explicitly does not measure JSDOM or the actual page ([`benchmarks/prisma-observer-benchmark.js:3-5`](../../../benchmarks/prisma-observer-benchmark.js)). Campaign History has a separate broad body/shadow-root observer and recursive navigation search ([`features/campaign-history.js:824-835`](../../../features/campaign-history.js), [`features/campaign-history.js:963-1027`](../../../features/campaign-history.js)). The observed scheduling result cannot establish acceptable CPU or responsiveness. | Profile signed-in Home, legacy/new Orders, Plan, Actualise, and non-Prisma Mediaocean pages in Chrome. Record CPU, long tasks, heap, content-script bytes, mutation frequency, and interactive latency before/after. First narrow History's observer to the navigation host and stop rescanning while its link remains attached; then split or gate feature bundles by host/path. |
| **Improve before wide scale** | **History and reporting need an explicit retention policy.** History is capped at 2,000 entries but no age expiry was found ([`features/campaign-history.js:7`](../../../features/campaign-history.js), [`features/campaign-history.js:552`](../../../features/campaign-history.js)). Stats use dated local records ([`background/stats-manager.js`](../../../background/stats-manager.js)); diagnostics have a seven-day event-age rule ([`background/diagnostics-manager.js:7-8`](../../../background/diagnostics-manager.js)). Reject or stream oversized CSVs with a friendly size limit, cap Meta pagination/results, and make long operations cancellable. |
| **Improve before wide scale** | **The feature catalogue and release docs need one owner.** README lists only a subset of the many Settings/Prisma features, while [`feature-settings-registry.js`](../../../feature-settings-registry.js), Settings, onboarding, Help Guides, and the in-extension release notes all describe behaviour independently. Current working-tree preview images and help/approval edits were already in progress. | Users and auditors may see differing descriptions, defaults, and scope. | Make a generated or checked feature matrix from the registry: audience, default, route, permission/data used, setting key, dependencies, help link, and smoke-test owner. | **Maintainability** | **Several feature modules are large and couple UI, state, parsing, and storage.** `social-finance.js` is about 143 KB, `settings.js` about 114 KB, `social-finance-engine.js` about 98 KB, and `campaign-history.js` about 87 KB. Start with the Approvers router contract and Approval Tracking storage queue. Keep behaviour and script order covered by existing tests; avoid a broad rewrite immediately before launch. |

## Confirmed strengths and limits

- The privileged clipboard reader has a sender/Mediaocean check, and the explicit **Paste Approvers** action rejects synthetic clicks. Offscreen clipboard messages require an internal extension sender. These controls should be kept while fixing the Favourites path.
- The feature master switch removes dynamically registered content scripts and fails off when startup state cannot be read ([`background/feature-mode.js`](../../../background/feature-mode.js)). It does not revoke installed manifest permissions.
- Meta API requests put the bearer token in an `Authorization` header rather than a URL. Its pagination follows response-provided HTTPS URLs without an explicit Graph-origin check ([`meta-report-api.js:64-125`](../../../meta-report-api.js)); attacker control of that API response was not established, so this is hardening work, not a confirmed token leak. Pin the origin and cap pages/rows anyway.
- Actualise combination already limits the number and size of input CSVs ([`features/actualise-export-all.js:23-24`](../../../features/actualise-export-all.js)). The bulk export enumerates visible paginator links ([`features/actualise-export-all.js:44-51`](../../../features/actualise-export-all.js)); verify off-window months on a campaign with more months than the current pager displays before claiming “every month.”
- The login assistant is opt-in at the start of its feature module ([`features/prisma-login-assistant.js:5-24`](../../../features/prisma-login-assistant.js)); retain opt-in and test its organisation-picker behaviour in a real signed-in flow. No password capture was identified in this review.
- No arbitrary external website messaging interface is declared in the manifest. This does not make Mediaocean page DOM/events trusted.

## Pilot and release acceptance

1. Fix the two clipboard boundaries, the Approvers integration, and the approval-polling race; add tests that cross the real router/storage paths. Triage the budget editor issue and block that feature from broad default enablement until a booking-owner test passes.
2. Implement the audience choice. A non-Prisma user must complete setup without visiting Prisma and retain relevant shared tools. A Prisma user must be able to complete or skip the live tour; both roles can change their choice later. Test fresh install, update from existing storage, restart, multiple Chrome profiles, inaccessible Prisma, and feature-mode off/on transitions.
3. Run the live matrix on supported Chrome with the unpacked build that exactly matches the release candidate: new/legacy Orders, Plan ↔ Actualise, virtualized/off-screen months, copy actions and hit targets, Approvers, account switching, notifications, Help Guides/SharePoint PDF, Meta import/API, narrow layouts, and non-Prisma pages. Record defects and owner sign-off. The source review cannot substitute for this gate.
4. Publish accurate data/permission disclosures and obtain privacy/IT approval for storage sync, token handling, history retention, remote styles, and release distribution. Package from an allowlist and record hash, commit, Chrome version, release date, update owner, and rollback procedure.
5. Pilot with a small set of booking and non-booking staff. Measure actual DOM/CPU cost, errors, wrong-value incidents, tour completion/skip, support queries, and opt-outs. Expand by cohort only after the pilot criteria are met.

For distribution, Chrome's [official installation guidance](https://developer.chrome.com/docs/extensions/how-to/distribute/install-extensions) and [enterprise publishing options](https://developer.chrome.com/docs/webstore/cws-enterprise) describe administrator-managed installation paths; IT should select the route that fits company policy. Chrome's [storage API documentation](https://developer.chrome.com/docs/extensions/reference/api/storage) documents the distinct local, sync, and session storage areas that the privacy disclosure should name.
